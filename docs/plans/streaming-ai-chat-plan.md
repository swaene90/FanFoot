# Streaming AI Chat Plan

## Goal

Stream assistant text into the React chat UI as it is generated by Ollama, Groq, and DeepSeek. Preserve the current league-aware prompt, provider/model selection, tool-call loop, ownership checks, antiforgery protection, and persisted chat sessions.

## Scope

- Add streaming only for new chat messages. Existing session read APIs remain unchanged.
- Use the providers' OpenAI-compatible Server-Sent Events (SSE) response format.
- Do not expose provider API keys, raw provider URLs, or tool results to the browser.
- Keep the existing non-streaming request path available until the streaming flow is verified.

## API Design

1. Add `POST /api/chat/messages/stream` beside the current message endpoint.
2. Require the same authentication, session ownership, league membership, and `X-CSRF-TOKEN` antiforgery validation as `POST /api/chat/messages`.
3. Accept the existing message payload: session ID, league ID, provider, model, and message.
4. Return `text/event-stream` with a small application event contract:
   - `token`: an assistant text fragment.
   - `status`: non-sensitive progress, such as `Looking up league context` or `Checking player news`.
   - `complete`: the saved session ID and final assistant message metadata.
   - `error`: a safe user-facing failure message; provider response bodies and secrets remain server-side.
5. Flush each event immediately and stop work when `HttpContext.RequestAborted` is cancelled.

## Provider Layer

1. Extend `LlmClient` with a streaming chat method returning an `IAsyncEnumerable` of provider-neutral chunks.
2. Send `stream: true` to Ollama's OpenAI-compatible endpoint, Groq, and DeepSeek.
3. Parse SSE incrementally, handling `data: [DONE]`, partial JSON frames, empty keep-alives, and provider error responses.
4. Add DTOs for streaming choice deltas, including content fragments, tool-call fragments, finish reasons, and usage where available.
5. Retain the existing non-streaming `ChatAsync` implementation as a fallback while the streaming path is rolled out.
6. Keep provider selection centralized in `LlmClient`; `ChatService` continues to depend only on provider-neutral messages and chunks.

## Tool Calls

1. Stream text chunks to the browser immediately only when the model is producing a final assistant response.
2. If a streamed response contains tool-call deltas, buffer and assemble the complete tool calls server-side instead of sending those deltas to the browser.
3. Execute the existing tool-call loop server-side, emit a non-sensitive `status` event, append the tool result to provider history, and make the next streamed model request.
4. Limit the loop to the existing three iterations and return a clear streamed error when a provider emits malformed tool arguments or exceeds the limit.
5. Persist only the completed final answer and complete history. Cancelled or failed streams must not create a partial assistant message.

## React Client

1. Add a streaming API helper using `fetch` with cookie credentials and the existing antiforgery header.
2. Parse the response body with `ReadableStream` and `TextDecoder`, including SSE frames split across network chunks.
3. Add an empty optimistic assistant bubble when a send begins, then append `token` text into that bubble.
4. Surface `status` messages as an accessible, non-persisted progress indicator.
5. Surface `error` messages through the existing alert treatment and preserve the user's sent message for retry.
6. On `complete`, replace the optimistic message list with the saved session history and set the session ID.
7. Abort the active request on New Chat, provider/model changes, route exit, or component unmount. Disable duplicate sends while a stream is active.
8. Preserve auto-scroll while allowing the user to scroll up without forcing the viewport back to the newest token.

## Verification

1. Unit-test SSE parsing with split frames, `[DONE]`, provider errors, malformed payloads, content deltas, and tool-call deltas.
2. Unit-test the chat service to verify tool calls are completed before final text is emitted and incomplete streams are not saved.
3. Controller-test authentication, antiforgery validation, ownership checks, cancellation, safe error events, and session persistence after completion.
4. Add React tests for incremental rendering, status/error announcements, cancellation, retry behavior, and model/provider controls remaining disabled during a stream.
5. Manually verify streaming with Ollama, Groq, and DeepSeek using a simple question and a tool-requiring league question.
6. Run `dotnet test`, `npm test`, `npm run build`, and `docker compose --profile local up --build -d --wait`.
